# Постоянный порядок обновления kobalt_ru

Это регламент каждого обновления upstream, не отчёт о завершённой работе.
Канонические состояние, решения, согласования и результаты — в
[`FB2_FORK_PLAN.md`](../FB2_FORK_PLAN.md). Текущая подготовка beta7 —
[активный план](beta7-integration.md), [RU-предложения](translation-proposal-beta7.md).

## 1. Зафиксировать исходную точку

- Прочитать `AGENTS.md`, план, `building.md`, `validation.md`; перед изменением
  данных/кэша — `storage.md`. Сохранить пользовательские изменения.
- Работать только в назначенной ветке сессии. В Arena не создавать другие
  ветки/worktrees, не переключаться и не публиковать tags/releases/PR без разрешения.
- Записать полный SHA upstream и форка, последний проверенный бинарный SHA,
  CI/artifact и отдельно подтверждения устройства. Docs-only SHA — не новый бинарник.
- Обновление на устройстве: закрыть приложение, сохранить весь `.adds/kobalt/`.
  Не сбрасывать прогресс или кэш ради новой версии; правила совместимости — в storage.

## 2. Полный аудит upstream и fork delta

- Получить конкретный release commit, прочитать release notes и **полный source diff**
  от предыдущей upstream-базы. Инвентаризировать также автоматически сливаемые файлы.
- Сверить все обязанности форка с картой интеграции в плане: FB2/publication,
  preprocessing/cache/notes, shared EPUB formatting/settings/progress, RU/locale/debug,
  About, UI styling/fonts/icons, sleep captions, платформенные assets/build/tests.
- Проверить изменения зависимостей, storage/defaults, lifecycle, shared UI и тестов.
  Пробный `git merge-tree` не начинает реальный merge и не доказывает корректность.
- Заранее записать конфликты, семантические риски и конкретные проверки. Отделять
  refactoring/перенос файлов от изменения поведения. Не возвращать отменённые
  quiet-frontlight/cache-cleanup и другую отложенную функциональность.

## 3. Согласовать перевод до изменения assets

- Получить полную дельту ключей EN: новые, изменённые и удалённые, включая Android.
  Сверить каждую строку с исходниками: место использования, действие, состояние,
  единицы, ошибки, значения defaults; паритета ключей недостаточно.
- Представить **весь список** EN → предлагаемый RU с длинами и placeholders.
  Отдельно перечислить предлагаемые изменения ранее согласованных строк.
- Проверить термины и реальный экранный контекст по пользовательским снимкам.
  Длина в символах — индикатор риска, не измерение ширины. Не сокращать смысл
  предупреждений ради EN-длины; проверять wrap/height и narrow-layout fallback.
- Остановиться для согласования. Точные пользовательские правки перенести
  дословно; статус остальных предложений не считать автоматически утверждённым.
  Только после согласования менять EN/RU assets через существующий strings pipeline.

## 4. Слить и адаптировать, не замораживать upstream

- Выполнить сопровождаемое слияние согласованного upstream SHA в текущую ветку.
  Разрешать конфликты с пониманием ответственности, затем повторно проверить auto-merge.
- Следовать новой структуре upstream. Изолировать fork policy в связных модулях
  с небольшим числом явных hooks, а не копировать старые Settings/About/EPUB экраны.
- FB2 использует общие развивающиеся formatting/settings/save/progress.
  Все новые настройки получают общую фабрику presentation/metrics и state/default/apply
  contracts. Не исправлять отдельный widget поверх общей проблемы оформления.
- Stock version/commit и отрисовка About неизменны; fork label/debug присоединяются
  в общей точке. Нижние вкладки и согласованные формулировки не переименовывать.
- Проверить cache policy по фактической DOM/CSS совместимости. Optional keys —
  явные defaults, без бессмысленного повышения schema или очистки данных.

## 5. Документы и тестовые материалы

- Вместе с изменением обновить план, AGENTS и пользовательскую инструкцию
  `fork-kobalt_ru.md`. В плане явно отметить done / pending / not run и оставшиеся риски.
- В `doc/` оставлять действующие инструкции, технические контракты и активные
  предложения/планы. После завершения перенести все значимые решения, источники,
  согласования, ограничения и результаты отдельного отчёта в план, проверить
  сохранность, исправить ссылки и только тогда удалить отчёт. Не оставлять его
  дубликат под новым именем. Технические сведения закреплять и в профильной инструкции.
- Исходные снимки устройства и отдельные пользовательские книги —
  [`tests/manual/`](../tests/manual/README.md). Записывать provenance и бинарный SHA;
  не перепаковывать книги и не дорисовывать screenshots. При перемещении сверять
  SHA-256 до/после и обновлять CI invocation. Generated galleries/build outputs —
  в ignored `build/`, portable fixtures — отдельно в `tests/fixtures/`.

## 6. Проверки и конкретный пакет

- Выполнить доступные offline checks: strings generation/tests/parity/placeholders,
  source/packaging contracts, `platforms/ci/test.sh` и `git diff --check`.
  Команды и полный список — в building/validation и разделе 7.5 плана.
- Выполнить затронутые native suites, focused EPUB/FB2/appearance/cache checks,
  отдельный real publisher EPUB regression и Kobo Qt5 build/package/content checks.
  Не ослаблять assertions ради прохождения. Проверить результат **конкретного SHA**.
- Полную native/UI/lifecycle/all-variant проверку отличать от focused/representative CI.
  При отсутствии SDK явно указать not run. Qt5 приоритетен; desktop/Android не
  блокируют эту ветку, но общий код должен оставаться переносимым.
- Commit без агентского coauthor (`git commit --no-verify`), проверить историю,
  push только текущей разрешённой ветки. Для docs-only результата допустим `[skip ci]`;
  если менялся CI/test invocation, его новый путь остаётся непроверенным запуском
  до следующего реального CI — зафиксировать это, не наследовать старый PASS.
- Передать пользователю SHA, ссылку на **успешный** CI и конкретный Qt5 artifact,
  изменения и оставшийся device checklist. Package PASS ≠ native PASS ≠ visual PASS.

## 7. Устройство и закрытие этапа

- Пользователь устанавливает указанный пакет и проверяет EPUB/FB2, сноски/popup,
  off/on, formatting/reflow, reopening/progress, shared UI, свет/сон/USB по рискам релиза.
- Новые screenshots привязать к этому бинарнику. Проверить перевод, род/термины,
  переполнение/wrap, checkbox/rows/dividers, вкладки и About; старые снимки не
  подтверждают новую компоновку. Не требовать pixel parity с KOReader без A/B.
- Результаты и неподтверждённые ограничения сохранить в плане. Новые исправления
  переводов снова согласовать; новый код повторно проверить и передать отдельным SHA.
- Закрывать этап только по фактическим подтверждениям. Следующий релиз начинает
  тот же цикл, а не повторное внедрение отменённых fork-особенностей.
