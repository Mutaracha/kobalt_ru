## Входы и исправление прежней оговорки

`test & diagnostic/4f2cecd1/diagnostics.zip`; 26682 события events.jsonl,
диапазон записанного UTC 16:31:21.352–16:56:03.792, 2026-11-24.
Также используется предыдущий архив `cfa10b9` / ace3c3c и пользовательский
stopwatch-протокол. Даты/UTC здесь — данные устройства, не дата анализа.

Пользователь уточнил: видимые заголовки тестовых книг были изменены **до первой
проверки**, файлы в прошлой и новой сериях идентичны. Прежняя оговорка о разных
входах между этими сериями снимается: их можно объединять как evidence.
Сами HYBRID и ACCURATE копии имеют разные заголовки и fingerprint, это не один
и тот же cache entry. Новых редактирований файлов между измерениями не было.

Во всех этих opening-phases retained_book_hit=false: это уже не retained-memory
повторы предыдущей серии. Для книги 1 соответствующие close cache saves дают
saved=false **7 из 7**, и ни одно из 7 основных открытий не имеет disk cache hit.
У книги 2 соответствующие saves true **7 из 7**, все пять измеренных reboot
повторов имеют disk cache hit и paginate всего 27–32 ms. Model load у них
989–1000 ms, при этом путь до видимой страницы занимает около 5 секунд — это
разные границы измерения, остаток не следует приписывать XML parse.

Таким образом, подозрение пользователя подтверждено: проблема книги 1 находится
в сохранении/доступности полного кэша и проявляется в обоих режимах. Она не
доказывает общий отказ FB2 cache или ошибку только Hybrid. После reboot у первой
книги есть saved_position=true, поэтому 034 намеренно не включает cold prefix;
при cache miss выполняется полная пагинация, что объясняет возврат к ~9 секундам.

Точная причина saved=false пока **не установлена**: событие не показывает
ранний return/имя/fingerprint/cache availability/write result. Нельзя объявлять
причиной размер/память/кириллический заголовок либо ослаблять проверки источника.
Следующая необходимая диагностика: структурированные причины отказа save и
lookup с признаками key/policy/name equality, cache scope, return code/mapping,
файловой ошибки; не логировать содержимое книги. Добавить resource-backed
regression именно на обеих реальных книгах, не только synthetic fixture.

## Выброс A2 и дополнительные открытия

Значение 16.45 s не следует считать стабильной стоимостью пагинации книги 1:
в 16:40:44.836 уже начинается другое opening; в 16:41:05.659 оно завершается
с error.opening_interrupted (20.823 s). Затем в 16:41:05.834 начинается новое
opening, завершающееся в 16:41:11.565. Session total 16.097 s включает больше,
чем собственные model_load=5.440 s / paginate=5.085 s первой книги.
Это свидетельство пересекающегося/отменяемого opening workload, не доказанная
причина каждого лишнего миллисекундного интервала. Авто-восстановление прошлой
книги вероятно по положению сразу после boot, но не устанавливается по одним
безымянным open-start: не приписывать ему книгу без дополнительного identity.

В архиве также есть несколько disk-cache hits с model_load около 19–23 s,
часть открытий прервана/сменена. Их нельзя добавлять в пять быстрых warm runs
книги 2 или считать штатным reopen книги 1. Они сохраняют отдельный вопрос:
почему cached DOM иногда заново пагинируется и почему отмена открытия не всегда
сразу освобождает следующий запрос. Нужна диагностика совместимости layout и
причин invalidation/restore; parsed cache hit не равен layout reuse.

## Аппаратная корректность и счётчик

По отдельной проверке пользователя на 034-2-HYBRID:
- переходы по главам, сноска/возврат — номера страниц совпадают;
- до полной готовности первая страница показывает 1 из 46, вторая — 2 из 46,
  третья и далее — «Расчёт…»; возврат на первые две снова показывает 1/2 из 46;
- после полной готовности счётчик правильный на всех страницах;
- после перезапуска книги счётчик также правильный.

Это аппаратное подтверждение завершённого обновления счётчика **в этом сценарии**,
а не наблюдение вечного «Расчёт…». Прежний риск bookFraction=-1/публикации
whole_book_ready остаётся code-review гипотезой для других путей, не установленной
причиной этого наблюдения. Нельзя описывать его как подтверждённое здесь зависание.

Подтверждён другой UI дефект: промежуточный page count частичной модели (46)
попадает в глобальный колонтитул первых двух страниц. До готовности полного
документа глобальные page fields должны последовательно показывать pending
«Расчёт…» (либо отдельно явно помеченную оценку), а не ложный точный итог prefix.
После full-ready — правильные полные page counts без сдвига позиции. Диагностика
должна разделить initial frame, neighbour capture и последующие frames, чтобы
найти утечку page provenance; не заменять механически все числа во всём UI.

## Фиксация результата / очередь

Подтверждены: ускорение первого new-book открытия двух FB2, настоящий быстрый
межпроцессный disk-cache path книги 2, корректные номера после полного подсчёта
и reopening в проверенном сценарии главы/сноски. Не приняты: cache lifecycle
книги 1, согласованность pending page fields первых двух страниц и все прочие
непройденные сценарии Hybrid. Production-приёмка 034 целиком не объявляется.

Приоритеты дальнейшей работы:
1. Причина save=false книги 1 + regression/save-close-new-session на реальном FB2.
2. Не выдавать prefix total за точный глобальный page count на initial frames.
3. Отдельно layout-cache compatibility/cancellation для дополнительных медленных
   cache-hit openings; не маскировать это ускорением первого открытия.
4. Полная новая Monotype Corsiva из 2e1d108 всё ещё требует явной интеграции;
   изменение архивного вложения само не меняло tested binary 4f2cecd1.

В этой фиксации изменены только evidence/docs, runtime и новый пакет не собирались.
