# FB2: возможность ускорения первого открытия через Hybrid

## Статус и границы

Анализ, не реализация. Базовый runtime: полная ordered series 010–060,
`3e652fdc`; исследованные engine/session файлы совпадают с деревом после 050
(060 меняет интеграцию сборки). Ни Hybrid, ни формат кэша не изменены.
Пользователь сообщает: повторное открытие из кэша уже очень быстрое.
Нет новых замеров холодного открытия текущей сборки на устройстве.

Отложенная правка перевода к **следующей сборке**: заменить пользовательскую
команду «Выйти из…» на «Закрыть…» (сохранив отдельный фирменный run Kobalt там,
где команда содержит имя приложения). Сейчас строка и runtime patch не меняются;
отдельную сборку ради этой правки не запускать.

У первой основной body имеет непустое name="СОДЕРЖАНИЕ": нельзя определять

картинки основным bottleneck по этим двум структурам нет.

## Почему настройка Hybrid сейчас не ускоряет raw FB2

В `src/engine/blaze/adapter/reader_source.cpp`:

- open явно сбрасывает для FB2 `firstSpineItem/lastSpineItem` в -1 и
  `slicePages_` в 0. Затем вызывается обычный полный `engine_->Render()`.
- `setChapterMode()` для FB2 принудительно делает `fast=false`.
- `showSpineItems()` для FB2 сбрасывает окно в полный документ.
- `prepareFullDocument()` требует активные slice и spine window. Для текущего
  FB2 эти условия не выполняются.

Это намеренные границы адаптации формата, не забытый переключатель Settings.
Просто удалить эти guards нельзя: `reader_slices.cpp` рассчитывает позиции,
длины, page estimates и переходы через EPUB DocFragment/spine. У native FB2
другая структура и XPointer. Preview (`reader_fb2.cpp::openFb2Preview`) умеет
сериализовать фрагмент для настройки внешнего вида, но не является корректным
главным документом для постоянных позиций, поиска и аннотаций.

Blaze уже предоставляет нужные строительные блоки: character-range layout
(`setKoblazeLayoutSlice`), отмену/приостановку, сохранение layout и background
whole-book build. Описание — `src/engine/blaze/UPSTREAM.md`, разделы Hybrid.
Но привязку этих механизмов к native FB2 ещё нужно проектировать и проверять.

## Где ожидается выигрыш

В прежних device-логах именно этой второй книги (не текущий cold benchmark)
пагинация занимала 19 247–25 415 ms, parse 1 510–1 823 ms, общий logged total
25 794–30 803 ms. См. `fb2-opening-device-comparison.md` с ограничениями выборки.
Это основание исследовать отложенный layout, а не обещание конкретных секунд
для `3e652fdc`. Исправленный кэш 033 уже решает другой сценарий — повторное
открытие. Его нельзя ухудшать ради cold-start оптимизации.

## Рекомендуемый путь эксперимента

**Полностью разобрать native FB2, но первоначально сверстать только диапазон
вокруг стартовой/сохранённой позиции.** Затем готовить соседний диапазон и полный
layout в фоне. Это не загрузка только начала XML и не конвертация FB2 в EPUB.

Плюсы: не меняются исходные DOM IDs, XPointer и правила notes/images. Можно
оставить description, все тела и binary доступными до первого layout. Экономим
прежде всего пагинацию; parse, исходный style pass и обязательные маркировки
не исчезают. Background full build может потребовать второй DOM: оценить память,
не предполагать безопасное одновременное использование одного mutable DOM.

Нужен format-aware слой: корень/длина основного body, координата диапазона и
позиция в нём; sibling notes/comments — не главы основного текста. Удержать
настоящие FB2 пути, не подделывать EPUB spine или переписывать сохранённые
позиции. Проверить поддержку диапазона в низкоуровневом renderer именно на FB2
root/body, не только в высокоуровневом адаптере.

Фоновая работа должна использовать существующий сериализованный engine scheduler:
CREngine globals не thread-safe. Свободный параллельный Render — не вариант.
Смена размера/шрифта, закрытие, sleep и новая книга отменяют/инвалидируют работу.
Переход к полному layout — на безопасном пользовательском действии с тем же
якорем, не внезапный скачок страницы во время чтения.

Сначала пробовать совместимый полный disk cache. Частичный layout нельзя записать
под видом готового полного и затереть быстрый warm path. Сохранить fingerprint,
policy/version и проверку изменившегося файла; успешная фоновая полная сборка
должна давать тот же полезный кэш для следующего открытия.

## Альтернативы

1. **Отложенная вёрстка на полном native DOM** — предпочтительный первый опыт:
   меньше риска миграции адресов; parse/style и память остаются ограничениями.
2. **Парсить только секции вокруг позиции** — потенциально дешевле на огромном
   XML, но требует индексирования, сохранения предков/ID/ссылок, notes и binary,
   включая ресурсы после body; сложнее совместимость путей и отмена.
3. **Синтетический EPUB/spine** — облегчает использование нынешнего Hybrid,
   но меняет адреса, семантику FB2 и кэш. Не рекомендуется как первая итерация.

## Обязательный протокол до решения о внедрении

- Обе исходные книги, одинаковые размер страницы/шрифты/оформление; Accurate
  против текущего Hybrid (baseline), затем experimental FB2 slices. Не менять
  пользовательские кэши/настройки без согласования; cold cache изолировать.
- Отдельно process-cold и disk-cache-cold; одинаковые условия FS cache, несколько
  повторов с медианой и разбросом. Не путать загрузочный кадр с читаемым текстом.
- Измерять tap→первый читаемый кадр, read/parse/style/markers/layout/paint,
  первый переход и границу диапазона, время полной готовности/сохранения кэша,
  peak RSS, задержку отмены. Desktop замеры не заменяют ARM/reader evidence.
- Начало книги, середина и конец, возврат сохранённой позиции, длинный абзац
  сборника; несколько body, сноски, оглавление и поиск за пределами диапазона,
  аннотации/выделения, смена оформления, sleep/close во время background build.
- Полный переход не теряет/дублирует текст и не сдвигает якорь. Страницы до
  полного подсчёта явно приблизительные; после него footer и Navigate обновлены
  согласованно. Ранее замеченное зависание estimate не считать решённым этим
  предложением и не переносить в новую реализацию.
- После close/reopen кэш остаётся быстрым; изменённый файл отвергается; partial
  cache не выдается за полный. EPUB и Accurate не регрессируют.

Вывод: технически направление обосновано, особенно для сборника, но это отдельная
адаптация Hybrid к native FB2, не включение существующей опции. Честное число
ускорения возможно только после прототипа и device замеров. В этой итерации
runtime не изменён и новая сборка не требуется.
